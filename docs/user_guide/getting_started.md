# First run: use synthetic data to run TRACE

This guide assumes you are new to machine learning workflows. Complete a small example first, inspect its model and prediction files, and then prepare your own data. Run every command in a terminal at the project root.

## Task naming

**Risk prediction** is the public name for predicting the risk of events after baseline. The YAML `task` value and training/demo command value are `longitudinal`; trained-model package directories and configuration filenames use `survival`. Both identifiers refer to Risk prediction.

TRACE first asks different modules to make predictions, combines their results, and decides whether to add another module. For example, questionnaire information and laboratory measurements can form two modules. The project supports two tasks:

| Question you want to answer | Task | Configuration value | Result to read |
| --- | --- | --- | --- |
| Estimate the probability of disease already present at baseline | Prevalent | `prevalent` | Calibrated disease probability |
| Estimate the risk of an event in the coming years | Risk prediction | `longitudinal` | Absolute risk at a specified horizon, such as `5y` or `10y` |

The synthetic examples run on CPU without UKB access. `D1` is a fictional endpoint. The results illustrate the software workflow.

The example generator fills in configuration paths directly, so **you do not need to set `TRACE_*` environment variables for this page**. For real data, the [direct-path YAML workflow](real_data.md#configure-paths-in-yaml) also saves paths without exports. The real data guide includes an optional environment-variable approach.

## 1. Find the project root

The project root should contain `pyproject.toml`, `README.md`, `src/`, `pipelines/`, and `examples/`. After downloading or cloning the source, open that directory in your terminal. If the downloaded or cloned directory is named `TRACE`:

```bash
cd TRACE
ls
```

If you are already at the project root, skip `cd TRACE`. Put paths containing spaces inside double quotes. The commands in this guide use a macOS/Linux bash or zsh terminal; do not enter them at Python's interactive `>>>` prompt.

## 2. Install the runtime environment once

The verified release environment uses **Python 3.13**. The package requires Python 3.10 or later; use 3.13 with the supplied dependency constraints to follow the verified setup. First, confirm that Python 3.13 is installed:

```bash
python3.13 --version
```

If the command is unavailable, install Python 3.13 from [Python.org](https://www.python.org/downloads/) before continuing. Create a dedicated project environment to keep its dependencies separate from other projects:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -c constraints/reproducible.txt -e '.[longitudinal]'
python -m pip check
python -c 'import trace_agent, lightgbm, xgboost; print("TRACE environment ready")'
trace --help
```

`pip check` should report no broken requirements, and the import check should print `TRACE environment ready`. The last command should list commands such as `prepare-data`, `train-modules`, `infer`, and `evaluate`, with no traceback. `trace` is the entry point installed for this environment; `python -m trace_agent --help` provides the same command help.

`.[longitudinal]` also installs XGBoost for the Risk prediction task; if you only use the prevalent task, you can install with `-c constraints/reproducible.txt -e .` and omit `xgboost` from the import check.

`-e` uses the code in the current source directory. Keep the entire directory: the workflows use its configuration templates and resources. Each time you open a new terminal, return to the project root and run `source .venv/bin/activate`. Run `deactivate` when you finish.

Use the supplied dependency constraints when installing. LightGBM 4.6.0 is required for compatible calibration behavior. See [dependency compatibility](../validation.md#dependencies) for details.

If installation or model loading fails, see the [troubleshooting guide](troubleshooting.md).

## 3. Generate your first small example

```bash
python examples/prepare_demo.py --task prevalent
```

On success, the command prints the generated directory and the next commands. The default directory is `data/demo/prevalent/`. All data are generated by the program:

- 180 fictional participants: 120 for training, 30 for validation, and 30 for testing;
- two modules, `M1` and `M2`, and one endpoint, `D1`;
- three fictional numeric features, `a`, `b`, and `c`;
- knowledge association and burden files;
- another 6 new participants without outcome labels, to demonstrate prediction after deployment.

Start by opening `features.csv`, `outcome.csv`, `splits.csv`, and `train.yaml`. You can view CSV files in a text editor or spreadsheet application. YAML files describe what to read, what to train, and where to write results.

The generator only accepts an output directory that does not yet exist, to avoid overwriting data. If the default directory already exists, you can continue using its configurations. To generate another example, choose a new directory, such as `--output data/demo/prevalent-2`, and use that directory in the later commands as well.

## 4. Train, predict, and evaluate with one command

```bash
python -m trace_agent run --config data/demo/prevalent/train.yaml
```

`run` executes `pipeline.steps` in the YAML file in order. You do not need to assemble arrays manually or find old models: this example fits models from raw features.

| Stage | What it does | File to check after completion |
| --- | --- | --- |
| `prepare-data` | Check identities and splits, and generate the labels needed by the program | `prepared/cohort_module_targets_manifest.json` |
| `train-modules` | Train the two modules separately and generate training OOF scores | `bank/module_bank_manifest.json` |
| `score-modules` | Assemble each participant's module predictions | `prepared/cohort_oof_probs.npy` |
| `train-integration` | Learn how to combine modules | `output/fusion_model.joblib` |
| `calibrate` | Adjust disease probabilities using the validation set | `output/calibration_model.joblib` |
| `train-planner` | Learn whether adding another module is worthwhile | `output/q_model.joblib` |
| `infer` | Generate participant risks, paths, and burden | `output/predictions.csv`, `output/agent_results.jsonl` |
| `evaluate` | Check prediction performance using only the test set | `output/evaluation.json` |

Paths in this table are relative to `data/demo/prevalent/`. OOF means that a training participant receives a score from a model that has not seen that participant's label; see the [concepts guide](concepts.md).

The example models train for 3 rounds and use the sample requirements saved in `train.yaml`. They start with `M1`, and consistency checks are disabled. A path may stop after that first module; use the output checks below to confirm the run completed.

## 5. Read the outputs and confirm success

Open `data/demo/prevalent/output/predictions.csv` in a spreadsheet application or text editor. Its header is `participant_id,D1`, followed by 180 participant rows in input order. `D1` contains the fictional endpoint's prevalent disease probability: `0.2` means a 20% model probability. The demo should have 180 nonempty predictions. In real data, an empty cell means an unavailable prediction, not zero risk.

Two JSON files explain the rest of the run:

- `evaluation.json` should contain `"split": "test"` and `"participants": 30`. It evaluates only the 30 test participants.
- `agent_results.jsonl` contains 180 participant records, with endpoint scores, selected modules, the action path and burden. Its endpoint summaries can be shortened by `output.top_endpoints`; the CSV contains all endpoints.

`run_manifest.json` records the generated CSV path, configuration and model provenance. The original `.npy` files remain available for programmatic analysis; see [how to read predictions](concepts.md#read-predictions) for masks, identities and JSON fields. Keep the `*.joblib.manifest.json` files beside the models and the manifests in `bank/` when moving models.

## 6. Predict for new participants without labels

After completing the previous step, run:

```bash
python -m trace_agent run --config data/demo/prevalent/predict_new.yaml
```

This executes only `score-modules → infer`, using the models just frozen, with no further training. `new_cohort/` contains participants, features, and feature lists, but no `outcome.csv` or split file. The catalog still declares an outcome path, but this mode does not open it.

Open `data/demo/prevalent/new_output/predictions.csv`. Expect the header `participant_id,D1` and six participant rows, each with a valid disease probability. The IDs should match `new_cohort/participants.csv` in the same order. Performance cannot be evaluated without observed outcomes, so this configuration has no `evaluate` step.

To use your own new cohort, prepare its participant and feature tables with the same columns and encodings, then follow the [prediction workflow](real_data.md#predict).

## 7. Try Risk prediction

```bash
python examples/prepare_demo.py --task longitudinal
python -m trace_agent run --config data/demo/longitudinal/train.yaml
python -m trace_agent run --config data/demo/longitudinal/predict_new.yaml
```

The steps are similar, but the models use event and follow-up times, and there is no separate prevalent probability calibration stage. Open `data/demo/longitudinal/output/predictions_5y.csv` and `predictions_10y.csv` for the two horizons. Each has the header `participant_id,D1` and 180 participant rows. The corresponding files in `new_output/` contain the six new participants.

Values are event probabilities between 0 and 1. A value of `0.2` in `predictions_10y.csv` means a model-estimated 20% risk within 10 years. For the same participant and endpoint, 10-year risk should be at least 5-year risk. Empty cells mean unavailable predictions. Exact values can vary with software versions; use the [automated output checks](demo_verification.md) to confirm identities, validity and workflow results.

TRACE writes a separate probability CSV for every available horizon. The retained `horizon_risks.npz` holds the same probability arrays for programmatic analysis; `final_scores.npy` contains Cox log-risk scores, which are not percentages. `evaluation.json` reports AUROC and log-loss separately for `5y` and `10y` on participants with known outcomes at each horizon.

## 8. Move on to your own data

After completing both demonstrations, choose your next step based on what you have:

| Materials you have | Next step |
| --- | --- |
| Raw numeric features and outcomes for each participant, and you want to retrain | Prepare a catalog and primary split using the [real data guide](real_data.md), then run `data/configs/<task>-train.yaml` from the [training workflow](real_data.md#train) |
| Frozen native models and new participants' features, and you want predictions | Prepare a new catalog, then run `data/configs/<task>-predict.yaml` from the [prediction workflow](real_data.md#predict) |
| Aligned module prediction arrays, and you want to train fusion/Q | Use the existing score bundle workflow in `train.yaml`; first verify score provenance and OOF |
| External model files or precomputed scores | They must match TRACE's [model and score formats](../data_contracts.md); check feature order and score scale before use |

Keep UKB data in the authorized environment. Public code can include fully synthetic examples, field descriptions, and runnable programs; real participant data and participant IDs do not belong in the public repository.

To add medical consistency checks, separately provide aligned contributions, weights, and evidence resources; see the [real data guide](real_data.md). The beginner examples do not generate these inputs.
